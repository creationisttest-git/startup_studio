Reference

The board, the stack, and what the words mean.

Three things the method assumes you already know. They were written down in the repository and never on this site, so unless you cloned it, you could not check them. This page fixes that.

1 > The board

Every project runs the same board, and it is the only work queue. Seven columns, and eight ticket statuses underneath them. The reason it is fixed rather than per project is that the agents are written against these exact names: change the shape and the team stops matching the tool.

Two statuses share the UAT column. A ticket arrives as uat and becomes uat_complete when you have accepted it, which is why the chip is there: a tested ticket has to be distinguishable from an untested one at a glance.

The two rules that make it worth having

Only QA moves a ticket into UAT, and only with test notes a person can follow. The agent that built the thing never certifies its own work. A ticket sitting in UAT with no test notes is a process failure, not a fast one.

Nothing leaves UAT without you. The team can take a ticket all the way to UAT on its own. Accepting it is yours, every time, and it is never automated away. That single boundary is the whole point of the board.

Two things the tool refuses rather than trusting anyone to remember. A person cannot set a ticket to Prod deployed, and a person cannot edit the build tag a ticket carries. Both belong to the agents, and both are the kind of rule that quietly stops being followed if it lives only in a document.

Two more are conventions rather than locks. Work is only ever created into Backlog or To Do, because a ticket appearing mid‑board has skipped the queue. And done means live in production: not merged, not on a test environment. Live.

Why a ticket, for everything

Anything you say becomes a ticket before the work starts and before you get a reply, and the PM confirms it in one line with the number. Chat is not searchable in February. The ticket is the record, so a decision you made once does not get re-argued in six weeks by people who cannot remember whether it was rejected on principle or on timing.

2 > The stack

Projects reach for this unless there is a stated reason not to. It is not a preference and it is not the newest thing available: it is the stack already proven on the most complete product in the studio.

The reason it is written down at all is not the bill. Across five projects the studio once ran three hosting providers, three datastores and three unrelated authorization models, which meant how is access actually enforced had a different answer in every project. That is the single highest-risk thing a reviewer has to check, and it should have one answer.

LayerDefaultWhy this one
FrameworkNext.js, TypeScript, TailwindAlready the team's strongest surface. React everywhere means one component idiom rather than one per project.
Data and authSupabase PostgresReal relational data with row-level security, and auth and file storage included. No second vendor holding half the answer.
HostingCloudflare PagesThe free tier covers a validation build, and it issues its own certificate in minutes.

AnalyticsGA4Free, and the funnel work is already understood.

Nothing bills for existing

Every layer above has a free tier that covers a validation build, and none of them charges for idle capacity. That is the property that matters when most projects are meant to be killed rather than scaled: an idea that did not work should cost nothing to have tried.

Free is not unlimited

The limits are usually account-wide, so another project's usage is what takes yours down. A database was planned, agreed and half-scripted before the dashboard refused to create it, because the plan allows two and both were already used by other products. Nothing was misconfigured. The capacity simply was not there, and nothing said so until the moment of creation.

Access is enforced in the database rather than in the application, so a permission cannot be bypassed by talking to the data API directly. Deviating from any of this is allowed and normal: the standard names the conditions under which a project should, and a deviation is recorded with an owner and a review date rather than quietly taken.

3 > Glossary

Every term the method uses that is not ordinary English. Each has its own address, so anything on this site can link straight to a definition rather than to this page and a hunt.

the studio
The one place that owns the team and the shared rules for every project. It is not a project itself and it never builds a product. Think of it as head office: it employs the staff and writes the handbook, and the projects are the offices they work in.
a project
One product, with its own repository, its own board and its own state. A project uses the team; it does not own it. Anything a project learns that would help the others is pushed back to the studio, which is the whole reason the studio exists.
roster
The full set of agents available to a project, used the way a sports team uses the word: the squad, not the players on the field today. Sixteen roles, each a written brief saying what that role owns, what it must refuse, and what it gets penalised for. A project's roster is generated, never hand-written.
role
One agent's brief. Product manager, tech lead, designer, QA, security reviewer and so on. A role is a document, not a program: it is what the agent is told about its job before it starts.
load
Whether the tool can actually read a role and register it as an agent you can call. A role can be present on disk, current, and identical to the source, and still not load, at which point that agent silently does not exist. Thirteen of sixteen were in exactly that state for weeks because of three invisible bytes at the front of each file, and every check in place at the time reported all clear. Presence is not loadability, and only loadability matters.
compose
Building a project's roster by combining the shared role with that project's own additions. Like a document assembled from a shared template plus a local addendum: the template stays one file, and each office gets a copy with its own details filled in.
UAT
User acceptance testing: the stage where the person who asked for the thing decides whether it is actually the thing. It is the one column on the board that belongs to you, and it is the reason the rest of the board can be automated.
stack card
One file per project describing what that project is built on and how it works, written once. Every role reads it, so nobody has to be told the stack sixteen times. It is the shared half of an overlay; the per-role half sits beside it.
overlay
The project-specific half of that combination. Facts about this project's stack, extra rules, or a shared rule deliberately waived. The waiver is the only kind that carries ceremony, because it is the only dangerous one: it needs an owner, a reason and a review date.
fragment
A rule that belongs to every role, written once and pulled into each one at compose time. Before fragments, changing one shared rule meant editing eleven files by hand, and an edit that tedious is an edit that does not get done. Eleven copies with ten updated looks exactly like eleven copies all updated.
drift
A project's copy of the team no longer matching the shared original. Silent by nature: a copy is correct on the day you make it and wrong from then on, and nothing announces the moment it diverges. One project ran a retired process for weeks. The health check reports drift and, importantly, which direction it went, because syncing over a local improvement destroys it and promoting a stale copy reverts everyone.
gate
A review that has to pass before work goes further, run by an agent that did not build the thing. Code review, content review, security review, mobile check. Each one reports what it found and changes nothing, so the agent that built the thing is never the one that signs it off.
the front door
The assessment an idea goes through before anything is built. Six leads argue it from their own disciplines, one paragraph each, and return build, kill, or park, with the one measure it is meant to move and the objections including the ones that lost. A kill is the gate working. If nothing is ever killed there, it is not assessing, it is rubber-stamping.
measure
What a piece of work is supposed to improve, agreed before it is built, with today's number where that is known. If nobody can name one, the idea is usually killed at that point, because there would be no version of next month in which anyone could say whether it worked.
reality check
A monthly reading of what a project actually did. Revenue, orders, sessions, cost. Declining to answer is valid and gets recorded; not being asked is not. Every project that has never taken one is named on every health check, so an unanswered month stays visible rather than forgotten.
the ceiling
The cap on how much can be in flight at once: two large things and three small ones. Reaching it is said out loud with the count rather than absorbed silently, so the next thing waits somewhere visible instead of joining a queue nobody is tracking.
warm start
The file a session reads on the way in to find out what is true right now: the single next action, what is deliberately unbuilt, and the decisions already settled so they are not re-argued. Written at the end of every session and loaded automatically at the start of the next, so picking the work back up does not depend on anyone remembering to open it.
proving a check
Deliberately breaking the thing a check exists to catch, and confirming the check goes red. A check nobody has ever watched fail is indistinguishable from one that always passes, and several here have turned out to be exactly that.
